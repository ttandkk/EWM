# DVLA 25 Hz and REASSEMBLE 30 Hz pretraining data

The two formal exports use the same episode-indexed event-frame convention: `meta/event_frames.json` describes the arrays, and `event_frames/episode_XXXXXX/.../frames_AAAAAA_BBBBBB.npz` stores uint8 `[time, 2, height, width]` `counts` with a clip ceiling of 15. RGB videos, original action/state fields, task metadata and episode tables are kept in each dataset's native LeRobot layout. The DVLA export has three event cameras and preserves its six 25 Hz video features; REASSEMBLE has one event camera and four 30 Hz video features.

| Property | REASSEMBLE export | DVLA 25 Hz export |
| --- | --- | --- |
| Rate and interval | 30 Hz, 33.3 ms | 25 Hz, 40 ms |
| Event-frame size | 260 x 346 | 360 x 480 |
| Event cameras | `event_cam` | `wrist_cam`, `side_cam`, `opst_cam` |
| Event values | 10 ms filtered real sparse-event counts | Number of active 4 ms subframes classified from H.264 polarity-render videos; not raw event counts |
| Disk channels → training channels | Source `0=OFF, 1=ON` → `[0,1]` | Source `blue=ON, red=OFF` → `[1,0]`, confirmed by sampled same-view brightness changes |
| RGB | `hand`, `hama1`, `hama2` | `wrist_cam`, `side_cam`, `opst_cam` |
| Action | 9-D absolute next observed EE pose `[x,y,z,qw,qx,qy,qz]` + two gripper positions | 10-D future EE target minus current state: position delta (3), Euler sin/cos component deltas (6), gripper (1); target reached 320 ms later |
| State | 36-D | 9-D, plus 9-D privileged environment state |

## Action semantics

REASSEMBLE is in end-effector **absolute pose space**, not joint torque/velocity space. The LeRobot port sets `action[i]` to the observed EE pose and two gripper positions at `i+1`; episode 21 was checked row by row. At 30 Hz this is a next-state label about 33.3 ms ahead, not a recorded control command.

DVLA is in an end-effector **relative target space**. Its 10 components are `[dx,dy,dz, d(sin rx),d(cos rx),d(sin ry),d(cos ry),d(sin rz),d(cos rz),gripper]`, with the pose-related deltas measured from the current 9-D EE state to a pose reached 320 ms later. The gripper component is preserved from the source action. In the 25 Hz export that future pose is about eight output frames ahead; the action is not the control executed during the next 40 ms.

These labels cannot be pooled into one action head by padding dimensions: they differ in absolute/relative form, rotation representation, gripper representation and target time. Use separate heads or a newly defined common target derived from both state trajectories. For causal event forecasting, do not supply either hindsight label as if it were the command known at observation time.

## Recommended joint pretraining contract

**Time: use the native-rate data as the first training baseline.** Read REASSEMBLE's existing 30 Hz frames and DVLA's 25 Hz frames directly. Sample 24 consecutive frames from each source and keep the model's current integer-step temporal positions; no REASSEMBLE re-export or event-count interpolation is required. The resulting real-time horizons differ: 24/30 = 0.80 s versus 24/25 = 0.96 s. For broad RGB/event representation pretraining this approximate timing is a reasonable first experiment, but it is not a claim that the two physical horizons are identical. Keep source identity and FPS in batch metadata, use the enabled homogeneous-source batches, and report evaluation separately on both sources. If this 20% duration difference later causes measurable rate confusion, then add an explicit `dt` embedding and scale event/action RoPE time coordinates by `30/fps` (after the current temporal-latent center calculation). A separate 25 Hz REASSEMBLE cache is optional only if a strict common physical grid becomes necessary.

**Space: retain native files, transform samples online.** Both event sensors are approximately 4:3. For the current 256x256 EWM input, resize each RGB/event view to 256x192, then pad 32 pixels above and below. Use an image interpolation method for RGB. For events, threshold each native polarity channel at `count > 0` *before* area downsampling; area interpolation then gives an activity fraction in `[0,1]` per output cell. Keep polarities separate and retain a valid-region mask; exclude padding from pixel-space metrics and mask or downweight the corresponding latent tokens during latent-space training. Do not center-crop a square, since it would discard side content. This online transform does not change either saved dataset's original resolution.

**Event values: start with polarity occupancy, not a common count scale.** REASSEMBLE values are filtered real-event counts; DVLA values count active subframes inferred from a lossy rendered video, so a DVLA count of 5 is not physically equivalent to five REASSEMBLE events. The common baseline above uses binary native activity followed by area resizing; feed the resulting two floating occupancy channels directly as `[0,1]`, **without** the Piper loader's `count / 15` normalization. Occupancy depends on window duration, so record the source FPS and evaluate each domain separately; explicit `dt` conditioning is an optional follow-up. The disk exports retain their original clipped counts for later ablations. If count strength helps, compare an additional source-specific `log1p(count)` transform calibrated on active pixels in each training split, with dataset identity supplied to the model. Never use signed polarity cancellation or a global histogram match that pretends the two count types are identical. The loader now canonicalizes channels to `[OFF, ON]`: REASSEMBLE uses disk indices `[0,1]`; DVLA swaps disk indices to `[1,0]`. REASSEMBLE polarity is defined by its official visualization code; DVLA blue=ON/red=OFF is supported by same-view RGB brightness checks across eight episodes and all three event cameras. The DVLA generation repository currently returns HTTP404, so this is a measured mapping rather than a recovered renderer definition. The original export metadata still records the earlier unverified state; raw files are unchanged.

**Training adapter:** `EWMMixedEventOnlyDataset` now reads both formal exports at their native 30/25 Hz rates. It uses the official 111-episode REASSEMBLE train split and DVLA's train split, decodes two current RGB views, and loads one current plus 24 future event frames. It never opens the action/state Parquet columns. The default event view is REASSEMBLE `event_cam` and DVLA `opst_cam`; the default RGB pair is REASSEMBLE `hama1`/`hand` and DVLA `opst_cam`/`wrist_cam`. The neutral prompt identifies the source. The loader checks `.export_complete` before training. It shuffles all valid windows within each source and interleaves homogeneous-source batch groups in proportion to the number of valid starts (approximately58:42). With multiple GPUs, all ranks share one source per micro-step. Source-tail padding adds fewer than one global batch of duplicates per source per epoch. Preserve the original action/state columns on disk for later objectives.

The mixed loader implements source camera roles, common spatial geometry, occupancy values and canonical polarity. It retains native-rate windows rather than equal physical durations. Its default `dataloader.homogeneous_source_batches=true` uses source-homogeneous batches, with the same source across all data-parallel ranks at each micro-step. Only the training split is supported; separate held-out validation still needs an evaluation adapter. Do not feed either dataset's preserved `action` field as a causal 33.3/40 ms control command: the source meanings differ and each contains future outcome information. A state-only/event-only pretraining objective or explicitly separate action heads can avoid silently mixing these labels.

DVLA frame `j` pairs RGB and tabular row `10j+9` from the 250 Hz source with the accumulated rendered event frames `10j..10j+9`. This is an index-level alignment; source event videos are lossy renderings, so the resulting counts are an approximation. REASSEMBLE's event frames use their original master-camera timestamp origin and have their own RGB nearest-sampling caveat; see `datasets/reassemble_training_eventframes_10ms/README.md`.

## Event-only training mode

Run `python scripts/train.py --config-name train_ewm_event_only` from `OpenWAM/` after both exports have `.export_complete`. On the current login node, prepend `/projects/hdd/myproject/CVPR2027/envs/torchcodec_ffmpeg7/lib` to `LD_LIBRARY_PATH` so the existing OpenCV import finds `libGL.so.1`. The Hydra config is `OpenWAM/configs/train_ewm_event_only.yaml`. It sets `model.training_mode=event_only` and `dataloader.type=ewm_mixed_event_only`. No existing export is rewritten.

In this mode, the EWM event branch attends only to event tokens. This computes the exact event-query result of masking every action/state key while skipping the unused action expert. The action/state tensors are absent from the batch, no action flow target or action noise is built, and `loss=loss_event` with `loss_action=0` for logging compatibility. The joint mode remains the default and retains the existing parameter/checkpoint layout. Event-only checkpoints retain untrained action weights; use event weights for transfer, and train the action branch separately before expecting action predictions.

The first run uses source-specific neutral prompts and one event camera per source. Event values are binary native activity followed by area resizing to 256x192 and 32-pixel top/bottom padding. RGB receives the same geometry with image resizing. The loader returns `valid_region_mask`; latent event loss and decoded diagnostics exclude the padded rows. Training channels are `[OFF, ON]`; DVLA disk blue/red channels are swapped online, while REASSEMBLE 0/1 channels retain their order. Same-length frame windows span different real durations (24/30 versus 24/25 seconds), so report validation separately per source. `sample_policy` in event-only mode returns event latents/frames without action fields.

## Verified defaults and preprocessing audit (2026-10-02, Asia/Shanghai)

The user-selected default is **Event D768 / Action D512, H8/L12/K24, LeanVAE-16 BF16, latent patch4, total spatial stride32, temporal stride4**. A latent patch4 groups4x4 VAE cells into one DiT token. LeanVAE has already reduced each spatial axis eight-fold, so the total image-to-token stride is8x4=32. At256x256 there are64 tokens per latent time slice and7 slices (observation plus six future groups), giving448 tokens for one event camera. Patch8 is an explicit stronger-compression alternative with total stride64 and112 tokens. The default therefore preserves more spatial tokens. The Piper Slurm launcher explicitly selects patch4/dual; the base and event-only defaults select patch4/wrist-only.

The reproducible audit and evidence are in `tmp/event_only_contract_audit/REPORT.md`, `audit.py`, and `results/audit.json`. Statistics sample24 windows of25 frames per source, using seed20261002 and valid-start-weighted sampling; all statistics below exclude the padded rows and describe the default DVLA `opst_cam` view. They are sample estimates, not a dataset-wide certification.

Representation, polarity, dtype, numeric range and model mapping are aligned. **The empirical distributions are not identical:** DVLA mean occupancy is about2.06x / 2.41x REASSEMBLE for OFF / ON, with stronger fractional coverage at active resized pixels. Different time windows, views, synthetic versus real sensing, filtering and H.264 rendering remain domain differences. Do not describe occupancy thresholding as equalizing event density, and do not divide DVLA values by15 or force histogram matching to conceal these differences. Retain source-specific prompts/FPS and report source-specific evaluation. Both sampled inputs have the same nonzero and `>1/30` fractions after resizing; decoded continuous predictions can still have values below this diagnostic threshold.

RGB inputs use uint8 `[0,255]`, Lanczos image resize to192x256 and the same zero padding; events use area averaging after thresholding. The loss downsamples `valid_region_mask` to the VAE latent32x32 grid and weights latent errors; decoded diagnostics exclude padding. It does not remove all VAE receptive-field effects near the padding boundary. Latents and velocity/noise are not restricted to the input occupancy range.

## Temporal overlap contract shared with Piper

All three sources use disjoint event accumulation intervals. Piper and REASSEMBLE use consecutive33.3ms intervals; DVLA uses disjoint groups of ten4ms rendered frames (40ms). REASSEMBLE frame i covers `(t0+(i-1)/30, t0+i/30]`; DVLA frame j covers source indices `[10j,10j+9]`. Neither loader extends an event accumulation window across adjacent frames. REASSEMBLE's10ms background-activity filter support is not its accumulation-window length.

Event-only explicitly matches Piper training-window sampling: `chunk_size=24`, `window_stride=1`, current event frame k and future event frames k+1..k+24, with current RGB at the anchor. Adjacent anchors share23 future targets and24 frames when including the observation. Samples stay within an episode and are shuffled for training. Thus event accumulation is non-overlapping while training clips overlap. Native30/25Hz rates are retained, so physical accumulation length and forecast duration remain source-specific (33.3/40ms and0.80/0.96s). This is alignment of window-overlap rules and frame counts, not equal physical timing.

## Source-homogeneous batch implementation

`dataloader.homogeneous_source_batches=true` is the event-only default. The sampler independently shuffles every source's valid window indices each epoch, forms groups of `training.batch_size * world_size`, and randomly interleaves source groups. It yields each group's per-GPU batches consecutively, matching Accelerate's non-split sharding. Every GPU therefore receives the same source at a micro-step, with the configured per-GPU batch size unchanged. Each source's final group is padded only from that source; all original windows are visited and fewer than one global batch of indices per source are repeated per epoch. Sampling remains approximately58:42 rather than forcing50:50.

Shuffling uses the shared run seed plus epoch and is replayable for full-state resume. The effective batching option is stored in the resolved config/resume contract. `homogeneous_source_batches=false` selects the previous mixed-source random batches. Accelerate `split_batches=true` is rejected for homogeneous grouping, since rank-sized batches are already emitted. Gradient accumulation may combine different source-homogeneous micro-batches within one optimizer update. Native30/25Hz timing and occupancy preprocessing are unchanged.
